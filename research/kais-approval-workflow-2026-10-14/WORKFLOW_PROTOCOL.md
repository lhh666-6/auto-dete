# 已审变更计划的审批与执行：应用依据及离线对照协议

2026-10-14；投稿后探索性工程验证。用户批准完成返修整理、具体工作流核准、按实际缺口对照及在线采集决策。规则在本轮留档执行前锁定；非预注册、无真人审批、无生产资源，不替换原冻结实验。

## 独立依据与选定工作流

采用基础设施配置变更的 **保存计划 → 审阅该计划 → 执行该计划** 流程。HashiCorp 官方 [Running Terraform in automation](https://developer.hashicorp.com/terraform/tutorials/automation/automate-terraform) 的 Interactive Approval of Plans 要求把两步连接，批准应对应正确计划，而非后来另一个计划。这支持明确审批对象的实际工程需求。

OpenTofu [apply](https://opentofu.org/docs/cli/commands/apply/) 把传入 saved plan 视为批准，直接执行其内容；[运行流程](https://opentofu.org/docs/cli/run/) 与 [plan](https://opentofu.org/docs/cli/commands/plan/) 说明保存计划的用途。CLI 本身不核对我们另存的人类审阅记录。不能把操作者主动传入另一计划却获执行，描述为 CLI 越权漏洞。

官方规则不证明“所有同语义重新生成的对象一律不可互换”，也不禁止相同计划文件的复制/搬运。本文对照的外部应用义务明确为：**外层流程已批准一个命名的计划产物，只执行这个产物；新计划可以重新批准；复制同一产物保留逻辑 ID 和内容摘要。** 它是官方审批流程的一种显式实施，非引用的通用法律规定。真实组织采用率和人工负担仍未测量。

选择 OpenTofu 1.13.1 原生 CLI（固定官方发布包与摘要）；内建 `terraform_data` 资源只管理本地状态，不调用云平台、第三方 provider 或 provisioner。它提供真实计划、状态持久化、版本检查；业务 fixture 是构造配置，不代表实际基础设施负载。所有工作目录限制在本实验的 runs 子目录。

## 比较方法及信任边界

两路均执行同一官方 CLI、同一资源配置、原生状态检查，使用相同外层产物绑定：

1. **saved_plan_binding**：官方推荐工作流的本地实现。可信审批记录绑定逻辑 artifact_id、计划文件 SHA-256 和批准值；执行包装器验证实际传入的产物与已批准记录匹配，随后调用原生 `tofu apply <saved-plan>`。逻辑 ID/摘要门是明确公开的工作流胶水代码，不冒充 OpenTofu 内部原生 API。
2. **binding_plus_correction_receipt**：保留上面全部逻辑，另加入纠错关系记录及其一致性检查：原提议计划/值、授权值、审阅计划标识、执行计划/结果。使用同样的原始计划和审阅信息。其目的为检查显式记录的集成可行性和额外本地记录量，**不是本文完整形式合约的移植或同层级研究系统复现**。

原生计划编译使纠错发生在最终计划审阅之前：提议配置 20，若需纠正则编辑为 21、生成新计划、审阅并批准新计划。不能沿用对原 20 计划的批准来声称已批准 21。原提议通过独立计划记录保留。这与论文中对候选授权替换值的执行关系并非逐字段同构，报告须说明差异。

两路都持有所有计划与审阅原始记录；不通过剥夺基线输入制造审计能力差距。增加结构化纠错记录不证明基线无法从自己的日志重建该关系。包装器与本地目录被假定可信；不测试对抗性文件系统、验证到使用间竞态、签名服务或分布式原子性。实际多资源 apply 不因此获得本文的单记录原子后继保证。

因此，本对照不能估计“实例绑定相较内容绑定的增益”：两路都绑定同一 artifact_id 与摘要。它检验已有强绑定流程上的纠错记录增量。原生前驱检查依据固定的 [v1.13.1 源码](https://github.com/opentofu/opentofu/blob/v1.13.1/internal/backend/local/backend_local.go)，本地快照与二进制版本一致。

## 固定场景

每个工作目录先以原生 CLI 建立值为 7 的本地资源；保留一个 reference_note 字段。Accept 的提议/授权值为 20/20；Correction 为 20/21。两种关系 × 以下六场景 × 两路，共 **24 条主记录**。不随机抽样、不估计风险率、不做显著性检验。具体命令、配置、审批记录、计划文件及状态全部保存。

| 场景 | 初始尝试 | 恢复 / 合法控制 |
|---|---|---|
| normal | 执行已批准的计划 | 原样重放，检查无第二次状态变更；原生是否拒绝/返回何种结果如实记录 |
| configuration_changed | 批准后把工作配置改成 99，仍传入已批准计划 | 检查原生使用计划内的已批准值；不把未使用新配置视作失败 |
| regenerated_equivalent | 重新生成相同业务效果、但登记为另一个逻辑产物的计划，沿用旧批准 | 两路产物门应要求回到已审计划或另行批准；选择复用已审计划作为一个确定性恢复见证 |
| different_plan | 尝试传入值为 42 的另一个计划，沿用旧批准 | 复用已审计划 |
| stale_state | 已审计划产生后，以另一个合法原生提交推进状态；再执行旧计划 | 重新计划、审阅、批准，再执行；保留原拒绝记录 |
| relocated_same_artifact | 复制已审计划至另一文件位置，保留逻辑 ID 与摘要，再执行 | 应允许搬运，不人为把路径当候选身份 |

主要事实：包装器决定、原生返回码、执行对象、最终业务值、前后状态 serial/lineage、是否产生研究内变更、未改字段是否保留、恢复步骤、原生 CLI 调用数、额外结构化记录字节。计数与数据量只用于描述集成开销，不代表生产性能、人力耗时或 Agent 效率。

附加控制单独保存：

- 在独立构造工作目录直接传入重新生成的等效计划给原生 CLI。若通过，按 CLI 的显式批准语义解释，不算已批准工作流的安全失败。
- 两路均允许一个新计划在取得新批准后执行。
- 纠错记录中的原提议值/授权值与实际对应计划不一致时，扩展路应阻止不一致记录继续执行；这是新增审计条件的自检，不给基线记业务失败。

## 评分、异常与决策

共同业务义务与新增审计条件分列；无“整体安全得分”。同样保护、同样结果、没有新增保证均为有效结果。不同意图/不同授权的命令不混成同一处理组。重放及合法恢复是脚本构造路径，不称 Agent 自发策略。

保留全部失败与原始输出；异常标 unknown，不丢弃。实现调试或协议偏离记录在结果中，不把看过源码和调试后的设计称为盲测。执行后至少在新的运行目录完整重建，规范化核对业务结果；随机资源 ID、时间、plan 摘要不要求跨运行相同。

**在线决策门槛：** 仅当发现一个现有证据未回答、在同一审批信息和合法动作集合下仍需 Agent 选择的恢复/代价问题，并且新增采集可能改变论文结论，才进入单独锁定的 pilot。若强基线已实现相同对象传递、差异仅为结构化记录，不扩大模型调用，写明 NO-GO 的理由及剩余应用边界。
