## 设计和实际执行

运行未修改的论文 Host 隔离副本。Accept（20→20）/Correction（20→21）× context/bound × 六种提交历史，共 **24 条主记录**；另有 **8 条控制**。所有条件均使用原已审候选，本次没有实例替换，所以不用于估计两种授权策略的差异。

恢复脚本仅持有提交前落盘的原请求及公开工具返回，固定执行一次原参数/原 key 重试，然后查询完整当前状态。故障历史和私有状态只用于环境注入与评分。每次调用前后保存 SQLite 并重新载入，保留响应、客户端观察和全部状态。

[协议](PROTOCOL.md)、执行器和三个原始依赖副本等六个文件在 **2026-10-14 09:25:45 UTC（北京时间17:25:45）** 锁定；独立静态审查在首次运行前完成。属于知情探索的执行前锁定，不称预注册。首次和独立新目录重建均使用该版本，无执行后改动锁定文件。

## 结果

每行包含两种关系×两种政策的四条记录。

| 提交历史 | 记录数 | 对本请求的正确报告 | 恢复阶段新增状态变更 |
|---|---:|---|---:|
| 首次请求未送达 | 4 | 重试后确认提交 | 每条1次 |
| 已提交并落盘，但成功响应丢失 | 4 | 重放确认历史成功 | 0 |
| 另一 key 使用同候选/授权提交相同值 | 4 | 本请求被拒；当前值仍达标 | 0 |
| 本请求已提交，随后 reviewer 停用 | 4 | 重放确认历史成功 | 0 |
| 本请求已提交，但重试通路仍受阻 | 4 | unknown；当前值达标 | 0 |
| 竞争请求已提交，本请求重试仍受阻 | 4 | unknown；当前值达标 | 0 |

主记录合计 **12 confirmed、4 rejected、8 unknown**；每条主记录最终均只有一条业务 transition，没有重复变更或虚假请求归因。8 条 unknown 是预设的信息不足控制，不能计为执行器错误或模型失败率。所有当前目标值都正确，也不等于所有主请求都成功。

两类控制各4条：

- 成功后同 key 改参数被拒为 `IDEMPOTENCY_COLLISION`；原参数重放仍返回原成功，不改变状态。碰撞不能作为“原请求未成功”的证据。
- reviewer 无效时的拒绝被缓存；reviewer 恢复后同 key 仍返回历史拒绝，合法新 key 可以成功。因此历史拒绝不代表当前永远不能执行。这里的新 key 仅用于该控制，不是主恢复策略。

两次运行均为 **316/316 检查通过，0 fail、0 error**。汇总中的36个通过项是24条主记录＋8条控制＋4组观察配对检查，不是36条独立轨迹。第二次运行用于复核，不能把样本量加倍。

## 有意义的发现及解释

**1. 当前状态相同，仍可能对应不同的请求归属。** 每种关系/政策有一对隐藏历史：一边由 primary key 提交，一边由 competing key 提交。两边完整客户端日志和全部公开观察完全相同，包含 `get_state` 的值、版本、来源和能力列表；私有持久化记录中的请求归属不同。这是四组具体的观察冲突见证。它说明本测试中的状态查询不足以完成请求归因；没有删减 state 信息来制造这一结果，也不证明所有接口永远无法消除歧义。

**2. 原 key 重放能补上归属证据。** 通路可用时，既有缓存成功/拒绝足以区分本次处理结果，不需要新恢复机制。请求尚未执行时，原 key 重试还能完成合法提交。这依赖完整原请求、缓存保留和本实验的完整持久化条件。

**3. 历史回执与当前权限应分开解释。** reviewer 停用后取回旧成功不产生新变更；旧成功返回的 `reviewer_valid=true` 描述的是历史决策。相反，reviewer 恢复后取回旧拒绝，也不代表当前仍无合法机会。这两种情况都由原系统已有语义处理。

上述事实与经典幂等 API 的处理思路一致；标准依据见 [AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。本次没有运行 AWS 服务，也不把请求标识、重放或回执当成新发明。
