# 提交结果不确定：已有机制的最小充分性验证

2026-10-14。用户同意先验证上一轮提出的第一条线索。本批为 **exploratory / 确定性机制检查**，无模型调用、无人类参与、不估计发生率或因果效应，不改投稿和既有队列。

## 问题与既有覆盖

OpenTofu 对成功后的重放和其他状态推进均可返回 stale plan，但上一轮 21/99 的完整状态可区分，不能据此声称不可消除的歧义。已有论文 Host 已实现同 key 精确重放、查询回执、旧授权防重复提交；原 R 与 runner 测试也已覆盖回执短暂不可用及提交后响应丢失的一部分行为。本次只检查组合场景及结果解释，不声称发明新的恢复机制。

独立设计核查指出：目标是区分“本 key 的提交得到确认”“本 key 的请求被拒绝”“本 key 的结果未知”；这不同于当前业务值是否达标，也不要求恢复者在无法观察时猜出原始网络故障位置。

标准方案依据包括 [AWS Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。本次运行的是未修改的原论文 Host；不是 AWS/OpenTofu 实现复现，也不是外部系统 benchmark。

## 运行载体、信息与信任边界

复制并锁定原 `kernel.py`、工具 schema、protocol manifest，保留原目录结构，以隔离副本导入运行。每个条件使用独立 SQLite 文件，完整 Host 快照落盘后重新 load，再恢复；保存调用和持久状态。恢复者持有在首个提交调用前写入磁盘的完整原参数及 idempotency key。

环境可以模拟请求未送达、已落盘后隐藏响应、reviewer_active 改变；这些属于明确的故障注入，不改 Host guard、幂等缓存或工具语义。不会模拟事务中途进程崩溃、部分持久化、跨服务副作用、缓存过期/淘汰、丢失客户端日志或恶意修改 key。成功落盘的快照恢复不是跨系统原子性证明。

恢复函数只接收客户端日志及工具回调，不接收场景名、私有 Host state、初次服务端结果或评分真值。所有情形给它相同的首次可见 timeout。完整 `get_state` 返回（包括 sources、version、capabilities）均可见，不删掉基线信息。若首次响应被隐藏，不能向客户端偷渡其中的 server commit_request_id。

固定恢复策略是：从持久客户端日志读取完全相同的原请求，**原 key 精确重试一次**，再读取完整当前 state。重试返回 ok 时只报告本 key 已确认提交，不推断提交发生在原调用还是重试期间；guard 拒绝时报告本 key 被拒，并独立报告当前值；传输仍未知时保留 unknown。恢复者不换 key、不申请新授权。该脚本是已有原语的合法恢复见证，不是 Agent 行为实验或最优恢复策略。

## 条件与固定判据

Accept（20→20）和 Correction（20→21）× context/bound × 以下六种历史，共 **24 条主记录**。两个 policy 在本次均使用原已审候选，不注入实例替换。使用同一初始已审状态克隆每个条件；每个克隆独立持久化，不相互影响。

| 条件 | 可信故障历史（仅评分可见） | 恢复者的正确报告 / 保护要求 |
|---|---|---|
| before_delivery | 首次请求未送达，客户端 timeout | 精确重试后确认本 key；总计一条 transition，恢复新增一条 |
| after_durable_commit | 本 key 已提交并落盘，响应隐藏 | 重试取原成功；确认本 key；恢复零新增 transition |
| competing_key_same_value | 首次本 key 未送达，另一 key 使用同候选/同 grant 合法提交相同值 | 本 key 重试被拒；当前值达标不能归因于本 key；不声称客户端识别了另一 key |
| committed_then_reviewer_disabled | 本 key 已落盘，响应隐藏，随后 reviewer_active=false | 精确重放确认历史成功，恢复零新增；不代表重新获得执行权限 |
| hidden_primary_commit | 本 key 已落盘，响应隐藏；恢复重试也在送达前被阻断，state 查询可用 | 本 key unknown，当前值可达标；不换 key再次执行 |
| hidden_competing_commit | 另一 key 使用同候选/同 grant 提交；本 key 首次未送达；恢复重试也未送达，state 可用 | 同上；与前一条件的完整公开观察必须完全相同 |

“另一 key”仅代表同一已审操作的竞争请求，不代表另一个人的独立审批、外部数据库写入或身份认证主体。后两项是共同信息不足控制，不计方法失败。完整公开 state 相同仍不证明所有接口都不足；在本测试中，能消除歧义的原请求重放通路恰被故障阻断。若该通路恢复，既有原语即可继续使用。

另做 2 类控制 × 两种关系 × 两种 policy，共 **8 条控制**：

1. 成功后同 key 改参数产生 IDEMPOTENCY_COLLISION；原 key 原参数仍返回成功，无新增变更。不能从 collision 推断该 key 从未成功。
2. reviewer 无效时的 guard 拒绝被缓存；恢复 reviewer 后原 key 原参数仍返回原拒绝；另一个新 key 的合法请求可成功。拒绝回执反映历史处理结果，不一定反映当前可提交性。

保留全部状态、原请求、私有故障记录、可见观察、错误和失败。异常执行记 unknown/error，不丢弃，不当作预期的信息 unknown 通过。完整快照重建后，按规范化业务结果复核一次；时间及派生证书摘要不要求跨运行相同。计数是构造条件数，不报告置信区间、p 值或模型成功率。

## 决策及停止条件

若原有机制在可获得回执的四类条件中能确认或拒绝本 key，在观测相同的两类条件中正确保留 unknown，且没有重复变更／虚假归因，则 **不为证明一个新机制而启动在线扩采**。它支持已有机制充分性的局部见证，不证明所有 Agent 都会正确调用它。

仅当发现现有完整原语仍无法满足一项合理、可核准的义务，并且能提出保留相同原始信息和保护的具体改进时，才另行设计后续研究。不能通过移除幂等重放、隐藏基线 source 信息、给新方法额外 oracle 真值或把 unknown 计失败制造收益。

设计依据来自源码和前次结果，属于知情探索；首次执行前锁定本协议、执行器和依赖副本。任何执行后修改另存版本并记录，不冒称预注册。
