# DSH 接续成果复核与补修

日期：2026-09-09。对象：r23 executable-checklist。

**结论：主体符合已批准方案，原交付仍有验证与表述问题；本轮已补修。** 无须推倒重做。该示例支持具体关系的作用，不应描述为行业系统比较或新增的通用理论证明。

## 符合要求的部分

- 两版共享不可修改的候选、完整版本快照、审批值/字段域/版本约束、CAS 和前后值审计。
- 9 个固定案例涵盖成功、替换、拒绝、回滚、来源继承与成对历史。
- 保留了公平的正面结果：基础版能从完整审计记录重建未修改字段来源。
- 成对历史具有相同候选池、提交值、审核人和版本，区别仅在审核时选中的候选；基础版的逻辑表状态相同，绑定版的审批表不同。
- 表格由运行记录生成，主体案例结果可以重现。
- DSH 修复的 Windows 测试连接泄漏有效，未改变被测政策。

## 发现并修复

1. **来源能力表述自相矛盾。** Supplement S3 原称基础版让 D_S “unbound”，但数据已证明两版均可重建来源。删除该断言，明确本控制没有显示显式来源表的额外重建收益；真正展示的是精确候选绑定及其支持的提案/授权值归属。
2. **运行器可覆盖旧证据。** `fresh_demo` 原先先删除同名数据库；原测试只证明底层 Demo 不覆盖。现在运行器遇到已有输出目录直接拒绝，底层创建也不删除旧文件。
3. **验证器漏检。** 原验证器接受配对历史分支未提交、来源继承第一步失败、成功案例值不正确和重复 case/policy 记录。新增 5 项回归测试，修复前均失败，修复后全部通过。
4. **观察范围不够精确。** “complete persisted database identical” 改为逻辑应用表状态一致；不将表级观测说成所有数据库物理信息的相同。
5. **计数口径不够清楚。** 新摘要区分 9 个案例、18 条 case/policy 记录（16 条单历史和 2 条配对历史）、20 个数据库执行。单历史的 5 次接受、11 次拒绝不包含配对分支，不构成统计成功率。
6. **文档与版本。** 更正 README 的 7/8 页矛盾；当前使用单独重跑目录，保留 DSH 旧记录；更新 AI 辅助声明和清单中的当前测试数量。

## 对 novelty 的实际意义

该例子将检查表从文字说明推进为可运行、可观察的设计对照。它展示：即便有事务、审批值与完整值审计，若未保存审核候选的绑定关系，仍不能区分指定的纠正/接受历史。它同时说明：完整审计已经能提供部分来源观察，显式来源指针不是唯一实现方式。

这使贡献边界更具体，没有把基础设计的正常能力算成失败。不要据此增加“优于现有系统”“五类关系都获得独立实验验证”或“第二套生产实现”的主张。
