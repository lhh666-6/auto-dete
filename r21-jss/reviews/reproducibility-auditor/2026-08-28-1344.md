# Reproducibility Audit Report

**Project:** AUTO-DECTE R21 JSS revision overlay  
**Date:** 2026-08-28  
**Auditor:** reproducibility-auditor (independent agent)

## Verdict: RED

The evidence and Python application lock are strong, but the R21 overlay cannot yet be rerun from a clean checkout on another machine: the advertised regression and live-agent checks depend on files or environments outside the manifested overlay, and the final R21 package manifest/handoff are not yet sealed.

## Scope and audit boundary

This was a read-only source audit. No project test, hosted-agent run, DSH run, performance benchmark, or manuscript build was executed. The review covered the R21 and paper READMEs, dependency and source pins, executable entry points, experiment configurations, manifest builders, paper build files, path/credential scans, output ledgers, and the documented boundary between the R21 overlay and the preserved R17 package.

The canonical paper input remains `evidence/reproduced/r21/live-agent-run-2`. At the final status recheck, `live-agent-run-3` was incomplete (22 files, no receipt or metadata, last write 13:41), while a separate `live-agent-run-4` process was still active (42 files, no receipt or metadata). Neither changes the audit of run-2, but both need an explicit noncanonical status before packaging.

## Replication Blockers (MUST FIX)

### 1. The advertised full Python regression depends on unmanifested parent-repository assets

`source/implementation/tests/conformance/alloy_projection.py::_find_research_root()` walks upward until it finds `formal/alloy/batch/auto_decte_batch.als`, then requires `tools/alloy-6.2.0.jar` and `tools/jre21/**/java.exe`. None of `formal/` or `tools/` exists inside the R21 overlay. They are found only because this working copy is nested under `D:\Claude_Design\auto-decte-paper`, outside the R21 revision manifest. At least eight formal-refinement test call sites invoke `run_projection`.

**Impact:** `uv run pytest -q` cannot reproduce the reported regression from a standalone R21 extraction, and the formal executable dependency is not protected by the R21 manifest.

**Required fix:** either package and hash the exact model, Alloy 6.2.0 JAR, and JRE 21 under R21 and resolve them relative to the overlay, or define the full repository checkout as the reproducibility root and extend the release manifest to cover those exact parent assets. Document their hashes and the expected test command.

### 2. The live-agent adapter is neither self-contained nor dependency locked

`source/live-agent-experiment/tests/test_server.py` hard-codes a Python executable under `revision.parents[1]/experiments/auto-decte/.venv/Scripts/python.exe`. That directory is outside R21 and is excluded by the repository `.gitignore`. Separately, `server.py` imports `mcp.server.fastmcp.FastMCP`, but R21 contains no live-agent `pyproject.toml`, requirements file, or lock, and the main implementation lock contains no `mcp` package. The runner also requires `codex.exe` on `PATH`, an authenticated account, a named hosted model alias, and compatible CLI behavior; the recorded run-2 metadata identifies `codex-cli 0.150.0-alpha.8`, but no executable hash or reproducible install instruction is provided.

**Impact:** the 12 live-agent adapter tests and six-scenario live run cannot be reproduced from the package on a new machine. Model-service drift means exact hosted output cannot be guaranteed, but the local adapter/server/test environment still must be reproducible.

**Required fix:** create a dedicated locked live-agent environment (or add `mcp` to a declared locked extra), replace the external-venv test path with `sys.executable` or an explicit CLI option/environment variable, document an exact offline test command, and document Codex CLI version/auth/model availability as a non-byte-deterministic external prerequisite. Record the MCP package version and, where distributable, the CLI executable identity.

### 3. R21 alone cannot regenerate the full paper evidence from raw baseline inputs

The README correctly states that R17 frozen raw evidence, runner, source manifest, and several-hour performance grid are not duplicated; only ten normalized manuscript inputs are carried forward. This is a good boundary statement, but there is currently no stable R21/R17 artifact URL or DOI, and the supplied public GitHub repository is explicitly documented as an older ESWA artifact.

**Impact:** a reviewer can rebuild tables from normalized JSON, but cannot independently rerun or verify the baseline raw-to-normalized path from the R21 deposit alone.

**Required fix:** co-deposit the preserved R17 package with R21, or provide a stable, checksum-bound R17 DOI/release and exact retrieval/verification instructions. The R21 release must pin a commit/release/DOI that actually contains R21, not the current older repository state.

### 4. The final delivery seal is not yet present and the handoff is stale

At audit time `evidence/r21-revision-manifest.json` did not exist, so the README command `python scripts/build_r21_manifest.py verify` necessarily has no current target. `FINAL_CODEX_HANDOFF.md` was still headed “R19” and reported 363 tests, 53 source files, 42 citations, and a 41-page paper, conflicting with the current R21 README and manuscript state.

**Impact:** the current directory has no final tamper-evident identity and the principal handoff gives an obsolete reproduction record.

**Required fix:** after all reports and paper outputs stop changing, rewrite the handoff for R21, build the non-self-referential R21 manifest, verify it from an independent copy, and only then publish the final hash. Do not build while run-4 is writing.

## Additional Gaps

### 5. DSH rerun instructions stop before an executable command

The official DSH release ZIP is present and matches `SOURCE_PIN.json`; its source tag, commit, release hash, and pnpm-lock hash are strong. The DSH README tells the reviewer to install and build the extracted workspace, but does not state where to extract it, how to wire the plugin into that workspace, the exact TypeScript runner command (`run_dsh_experiment OUTPUT IMPLEMENTATION PYTHON DSH_ROOT`), or how D10 assembly/normalization follows D1–D9.

**Recommendation:** add copy-paste PowerShell commands from archive extraction through typecheck, fresh output creation, final evidence assembly, normalization, and offline receipt verification. Keep the existing non-overwrite warning.

### 6. Paper and figure system prerequisites are underspecified

The paper uses `elsarticle`, `elsarticle-harv`, and several LaTeX packages, but no TeX distribution/package snapshot is supplied. The documented `latexmk` command requires Perl and is known not to run on the current host; the fallback is described only as an arrow sequence. Figure generation relies on available Arial/Helvetica/Liberation Sans fonts, and Matplotlib PDF/SVG metadata and font selection can vary across machines, so output hashes need not be byte-identical even when the plot is semantically identical.

**Recommendation:** document the tested MiKTeX/TeX Live and Perl versions, list the exact four fallback commands, identify required packages, set/record deterministic figure metadata and font assets if byte identity is required, and store the figure manifest source as a package-relative path.

### 7. Release selection is not yet clean enough for handoff

The R21 directory currently contains a 429,274,240-byte Windows `.venv`, about 40.9 MB of mypy cache, Hypothesis/pytest/Ruff caches, and active/incomplete live-agent directories. `build_r21_manifest.py` excludes the environment and caches, but there is no release-copy command that materializes only the selected files. The repository `.gitignore` also does not exclude revision-local `.venv`/cache directories.

**Recommendation:** create a non-destructive allowlist-based release builder from `selected_files()`, exclude or explicitly classify noncanonical run-3/run-4, and validate the resulting clean copy rather than zipping the working directory. Preserve diagnostic runs outside the citable release; do not delete provenance.

## Strengths

- The Python application has a hash-bearing `uv.lock` with an exact Python 3.11 resolution and platform-specific wheels.
- R21 benchmark configs declare seeds, warmups, trial counts, grids, and non-overwriting destinations.
- The R17/R18/R19/R21 evidence boundary is explicit: ten baseline normalized inputs are not conflated with the five later isolated inputs.
- The R21 paper-input manifest binds three inputs, two generated tables, 77 source-evidence files, and all canonical run-2 scenario artifacts.
- The DSH release archive matches its declared SHA-256 and pins the upstream tag, commit, and pnpm lock.
- Claim/evidence traceability is strong: 11 ledger claims map to concrete JSON paths, excluded claims are explicit, and generated tables/figures have named builders.
- Experiment runners reject existing output directories, reducing accidental evidence overwrite.
- No `.env`, credential, secret, or API-key file was found in the audited package.

## Recommendations

1. **Make the R21 regression root self-contained** (0.5–1 day): package/manifest Alloy + JRE assets or redefine and seal the full-repository root.
2. **Lock and decouple the live-agent environment** (0.5 day): dependency extra/lock, `sys.executable` tests, exact offline command, external-service note.
3. **Publish a two-layer artifact lineage** (0.5 day plus upload): stable R17 ancestor reference and an R21 release/DOI pinned to the actual revision.
4. **Seal the final R21 delivery** (1–2 hours after all writers stop): update handoff, classify run-3/run-4, build/verify/tamper-test manifest.
5. **Complete DSH and paper replication recipes** (2–4 hours): exact extraction/build/run commands and TeX prerequisites/fallback commands.
6. **Build a clean allowlisted release copy** (1–2 hours): exclude local environments/caches while retaining diagnostic provenance outside the citable package.
