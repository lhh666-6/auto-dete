# 五类准入区分：设计检查表填写说明

这份表把论文 C1–C2 转为开发者可使用的检查步骤。英文版 admission-design-checklist.md 包含完整五行表格、填写模板与源码依据，可随论文复现包交付。

## 怎么填

1. 选定系统版本和测试环境，写明哪些对象是候选、授权、权威记录，以及一次提交应包含哪些实际变更。
2. 逐项找到保存信息的对象或字段，并写出真正执行校验的位置。只填写“有事务”“有日志”不够。
3. 每项先运行合法对照，再运行对应失败探针。记录预期、实际结果和持久化证据路径。
4. 没运行就填 NOT RUN；只有合法对照与失败探针都有证据，才能填 SUPPORTED FOR THIS PROBE。该状态只对这次检查有效。

| 类别 | 最直接的检查问题 | 典型验证 |
|---|---|---|
| D_C 候选与上下文 | 人工授权指向的是哪个精确候选？ | 用另一个上下文中的等值候选替换，检查是否拒绝且无权威写入。 |
| D_V 值与责任角色 | 能区分机器提出 100、人工批准 101、实际保存 101 吗？ | 合法纠正应成功；重建结果必须保留原候选和人工授权角色，不能误记成机器提出 101。 |
| D_F 新鲜度 | 批准所依据的前驱在提交时还有效吗？ | 先提交其他合法后继，再重放旧授权；比较重放前后的当前状态，并检查并发竞争。 |
| D_B 批次完整性 | 这次实际变更是否只形成一个完整后继？ | 两字段变更中途注入失败，观察恢复结果和提交历史，不能只检查最终数值。 |
| D_S 字段来源 | 每个字段是否有唯一且正确的来源，未变字段是否保留原来源？ | 数值不变，破坏来源。提交前错误应被阻止；提交后损坏应在溯源时报告。 |

## 两个特别注意点

D_B 不要求所有人工提交项都成为新变更。当前实现允许混合提交，未变字段沿用原来源。D_S 也不等于完整 P6：后者还检查授权—候选—证据等整条链。

测试失败注入只能在隔离环境执行。若数据库约束已经阻止构造错误状态，应记录约束阻止的证据，不要编造后续溯源结果。这些操作性探针不能替代 Proposition 1 的数学投影证明。

这不是给论文认知输出做盲标的表：它面向系统开发者的设计检查。所有填写项保持空白，没有新增实验结果或跨系统验证结论。
