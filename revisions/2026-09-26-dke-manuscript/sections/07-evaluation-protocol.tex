\section{Evaluation protocol}
\label{sec:evaluation}

\subsection{Research questions and evidence status}

The evaluation separates relational correctness, the boundary at which review becomes authorization, and implementation cost:
\begin{description}[leftmargin=2.6em,labelwidth=2.1em]
\item[RQ1] Do the formal and concrete checks support the admission contract, and what changes when a rich event journal records the exact reviewed candidate?
\item[RQ2] Which inconsistencies between recorded review intent and confirmation can server-held session binding reject, and which remain outside its guarantee?
\item[RQ3] What admission, reverse-trace, and storage costs occur on the repaired implementation under the declared workloads?
\end{description}

We retain the earlier bounded analysis and concrete checks as supporting evidence and add three experiments, E1--E3, corresponding to these questions. The new experiments use the equality-repaired implementation at source commit \code{c6d512843c905cab6d8521dd8c914f7fb26d85ae}, under \code{latest/code/implementation-fixed}. The protocol was written before collection on 23 September 2026, with documented pilot corrections; it was not externally preregistered. Source hashes, scripts, pilot outputs, final receipts, database snapshots, and per-trial measurements are deposited. No hosted model was called for E1--E3. Historical hosted-agent runs provide separate integration context and are not counted as new security experiments.

\subsection{RQ1: correctness and comparison with a rich event journal}

\paragraph{Retained checks}
The bounded analysis executes 36 commands in each of two Alloy profiles. Concrete-to-formal checks cover nine intended projections and twenty mapping mutants. A 35-case production-facing catalogue distinguishes successful admission, zero-write rejection, and detection of post-persistence corruption. Stateful tests compare an independently maintained value/source model with persisted snapshots and traces; rollback and concurrency tests exercise transaction failpoints and contending calls. Their original manifests and execution environments remain identified separately in the supplement. They are not all claimed to have been rerun for the new measurements. Before E1--E3, 85 relevant implementation regression tests and ten experiment-harness checks were rerun.

\paragraph{E1 mechanisms and policies}
We wrote a separate \code{sqlite3} event-journal comparator for this study. Both its configurations retain immutable candidates and events, review context, version checks, transactional updates, and complete field-source maps. \emph{Context journal} records the field, version, evidence, and retained review context but omits the exact reviewed-candidate identity. \emph{Exact journal} additionally binds that identity. The third arm calls the reference implementation's actual transactional admission path. The comparator is a same-study implementation, not an externally deployed system or an independent-team replication.

We score two policies. The \emph{instance policy} requires the authorized candidate instance; the \emph{value/context policy} permits a different instance with the same retained review observations. The latter still checks field, version, evidence, and context, rather than value equality alone. Its projection omits certificate identifier, internal candidate identifier, and instance creation timestamp. Reporting both policies makes the cost of stricter identity requirements explicit.

\paragraph{Inputs and cases}
Twelve archived proposal cells are selected deterministically across three historical configurations and four benign scenario labels: the first lexicographic run containing a proposal is used, without selecting on task success. The selected configurations yield the same proposal in each scenario, giving only four distinct archived values: 8, 100, \code{B-008}, and 9. Three synthetic controls add integer/float, integer/Boolean, and nested numeric-type boundaries. Thus the fifteen inputs contain seven distinct proposal values. They are mapped into constructed form histories with newly prepared certificates and review events, not replayed as complete original workflows. Evidence substitutions manipulate constructed metadata rather than real image contents.

Each input exercises eleven case families: Accept, Correction, multi-field admission, same-value candidate substitution, different-evidence substitution, stale authorization, replay, unauthorized value, and interruption after CAS, before transition insertion, or before commit. This gives $15\times11\times3=495$ executions. The three interruption families examine rollback locations, not three independent adversary models.

\paragraph{Oracles}
An independent database reader checks proposal value, authorized value, reviewer, reviewed candidate, current value, and source version for each of three fields after successful admission: eighteen answers per accepted case. Answers are classified as correct, wrong, ambiguous, or unavailable. Rejection compares logical fact-database digests immediately before and after admission. The starting point is \emph{after authorization preparation}: the journal may already have persisted review intent, while the reference adapter captures the service-generated admission bundle before submitting it to the actual transaction. Zero-write rejection therefore concerns fact admission, not erasure of prior review events. Error reasons are checked against expected constraints or injected interruptions, rather than treating any exception as success. The original strengthened-baseline cases are rerun separately as continuity checks and excluded from the 495-execution denominator.

\subsection{RQ2: review-to-confirmation boundary}

E2 uses local Chrome and Playwright with a newly instrumented review-page fixture backed by the original \code{ReviewForms.confirm} service. An independent driver reads the displayed candidate identifier, proposal, and authorized value from the DOM before the authorization click. We compare the original confirmation path with an experimental server-held session gate binding candidate, version, reviewer, and authorized value.

Three JSON inputs (100, 2.5, and \code{true}) cross ten interactions and two paths, giving sixty browser cases. Six initial confirmations prepare replay cases and are additional setup operations. Accept, Correction, and legitimate reselection are positive controls. Candidate, authorized-value, and principal request substitutions test agreement with recorded review intent. Stale state, replay, and precommit interruption test rejection. A DOM-only substitution changes the displayed candidate while leaving the server and request target unchanged. The decimal input avoids JavaScript serializing an integral float as an integer.

We record agreement with the observed review, acceptance, and fact writes on rejection. This is a scripted boundary experiment, not a security evaluation of the original product UI or a human-subject study. Fixed trusted principal labels replace authentication. The gate's session database is separate from the fact database; the experiment does not establish cross-database crash atomicity, hostile-host resistance, or human attention.

\subsection{RQ3: repaired-version cost characterization}

E3 ran on an Intel Core i7-10875H machine with Windows 10 build 19045, CPython 3.11.16, SQLite 3.53.1, and SQLAlchemy 2.0.51. Operating-system background activity was not controlled. Each comparison cell uses five warmups and 200 timed executions per arm, randomly interleaved with seed 20260923. Two ten-cell admission comparisons contribute 4,000 observations each; a 36-cell trace comparison contributes 14,400. The total is 22,400 timed observations, excluding warmups. These repeated measurements do not represent independent deployment samples. Historical pre-repair timings are not pooled with E3 or used to calculate its ratios.

\paragraph{Admission}
The ten cells use 1, 8, 32, or 128 fields, with one, four, or all fields changed where distinct and feasible. The first comparison measures complete reference and exact-journal confirmation on a shared workload with recognition candidates registered before confirmation. Result queries must agree, including retained sources for unchanged fields. Admission uses SQLite DELETE journaling and FULL synchronization.

The timer covers the confirmation call, excluding database cloning and adapter construction. The journal opens its connection eagerly during construction; the reference ORM obtains its first connection lazily inside the call. Schema, ORM, and certificate-validation work also differ, and the journal does not implement every reference-application feature. Consequently this is an interface-boundary cost characterization, not a connection-controlled microbenchmark, a feature-identical system competition, or an isolated measurement of binding overhead. Different SQL hooks count trigger execution differently, so absolute cross-implementation SQL totals are not compared.

The second comparison is a separate prevalidated-materialization ablation using manual sources. A full admission generates a valid relational delta outside the materialization timer. Applying this delta retains complete snapshots, source maps, authority rows, transactionality, and CAS, but moves validation and planning outside the timed region. Each resulting state is checked against the precomputed reference fingerprint. Generated review identifiers and timestamps preclude a claim of byte-identical databases across independently executed full admissions. The two comparisons use different source workloads; their full-path columns must not be cross-subtracted.

\paragraph{Trace and storage}
The trace grid crosses 1, 8, 32, and 128 fields; 1, 10, and 100 versions; and 1, 100, and 1,000 total records. Both arms use the same current verifier. The point-read arm replaces three bulk repository reads---certificates, certificate--evidence associations, and transitions---with identifier enumeration and actual point lookups. Valid unrelated forms are seeded once and copied as database snapshots outside timing. After every invocation, the complete returned trace object must equal the counterpart result. This isolates an access-pattern change within the current verifier, not a reconstruction of the historical implementation.

Storage fixtures directly populate full and reduced schemas at 1,000, 10,000, and 100,000 transitions, using WAL/NORMAL and checkpointing before measuring the main database. They use single-field version growth and stable evidence references. The measurement excludes external images and model-output files. Direct population characterizes schema footprint; it neither demonstrates successful admission of every row nor makes the reduced schema audit-equivalent.

\subsection{Historical hosted-agent integration context}

The archived matrix contains $3\times3\times14\times10=1{,}260$ planned executions across three qualified configurations, three prompt variants, fourteen scenarios, and ten repetitions. The historical configurations are G1 (\code{gpt-5.6-luna}), G2 (\code{gpt-5.6-terra}), and D1 (\code{deepseek-v4-flash}); endpoint names are metadata, not immutable weight identifiers. A pilot qualification rule preceded the matrix; all planned final runs, including runtime failures, were retained. The exposed tools allowed proposal and verification, with confirmation reserved for the host.

For 360 benign runs, the original strict criterion requires specified exact call sequences; a post-hoc endpoint sensitivity permits extra calls while requiring the intended proposal and verification outcome. The stale scenario's strict criterion also requires the word \code{stale}. Behavior-evaluable runs have sufficient evidence for scoring regardless of task success. Planned-run yield and conditional completion are reported separately; unscored cases receive no imputed verdict.

Host authority checks are a different endpoint: 720 admission attempts use fixed host-constructed invalid tuples, while 179 capability-unavailable checks make no admission call. Neither branch derives its challenge parameters from the model answer. Unauthorized mutation means failure to reject when rejection is expected or a changed authoritative-state digest. Their counts describe executed integration checks, not model-generated attack efficacy or population failure probabilities. Supplement S5 summarizes historical endpoints and annotation; original prompts, qualification and scoring rules, missingness, and author-involved annotation records remain in the artifact.
